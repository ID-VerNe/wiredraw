# 合并评审（评审契约与派发）

> 本文件是**合并评审这件事的唯一归属**。`doc/PR_GUIDE.md` 的「合并评审」节只做引用，
> 不再重复散文——散文一分散就会两边说法不一致。
> 配套：流程总览见 [AGENTS.md](../AGENTS.md) §0 第 4 步；PR 其它规范见 [PR_GUIDE.md](PR_GUIDE.md)。

## 定位：评审权在谁手里

- **合并审批权归全新上下文的 subagent**。提交者把文档写完、门禁跑绿之后派发，
  评审出 `APPROVE` 就由提交者直接合并（merge commit），不需要维护者逐 PR 点头。
- **提交者不能给自己评审**，也不能「顺手」替评审者下结论。
- **脚本不评审、不合并**。`scripts/review_prompt.py` 只生成派发物料，
  `scripts/check_pr_sections.py` 只校验正文结构。
  一旦工具能自己出 `APPROVE`，这条门禁就退化成橡皮章——那正是它要防的东西。

| 角色 | 能做 | 不能做 |
|---|---|---|
| 派发者（提交者） | 生成派发文案、回答「文件在哪」这类定位问题 | 把自己的结论/辩解塞进派发物料、催结论、替评审者复述 diff |
| 评审者（全新上下文） | 读 diff、跑门禁、查磁盘、出 `APPROVE`/`REQUEST_CHANGES` | 采信 PR 正文的转述、引用别人的绿、在没有证据时下结论 |

## 派发物料怎么来

**不要手写派发文案。** 手写就一定会夹带提交者的叙述，而这个缺陷在事后无法检查。

```bash
python scripts/review_prompt.py --pr <PR 号>
```

它用 `gh pr view` 拉元信息（编号 / 标题 / base / head / 作者 / 链接 / 改动文件），
输出一段可直接粘给 subagent 的 prompt。关键设计：**默认不输出 PR 正文**，
只给「自己去 `gh pr view <N>` 读」的指令。

- 这样「不投喂提交者的结论」是**结构性保证**，不是靠派发者自觉。
- 逃生口 `--with-body` 存在，但会打印显式警告——它只在「评审者读不到 GitHub」时用。
- 输出里会标出「涉及门禁链：是/否」，评审者据此决定要不要走
  [PR_GUIDE.md「门禁改动与独立复核」](PR_GUIDE.md#门禁改动与独立复核) 那份清单。

### 派发者在派发时要做的

1. 跑上面那条命令，把输出**原样**交给 subagent，不改写、不补充、不加前言。
2. 确认 subagent 是**新会话**，不是本 PR 的作者会话。
3. 除「仓库路径 / PR 号 / 契约文件位置」外，不主动提供别的事实。
   被问到「你跑绿了吗」时，回答「自己跑一遍」——不要提供转述。

## 评审者必做清单

默认怀疑，**只信自己跑出来的东西**。

1. **读契约**：先读本文件，再读 PR 正文（`gh pr view <N> --json body`）与 diff
   （`gh pr diff <N>`）。
2. **完成声明以磁盘为准**：正文里每一句「已经做了什么」，都要在 PR 分支的文件里找到对应
   实体（文件存在性、`文件:行号` 引用是否指向真内容、门禁清单是否真有那条）。
   找不到就是没做。
3. **自己复跑门禁**：在 PR 分支的 worktree 里跑 `python scripts/run_gates.py ci`，
   贴**原始输出**。不采信 PR 正文里转述的绿，也不采信「CI 是绿的」。
   动过 `tools/android-mtp-probe/` 的再跑 `manual` 档。
4. **门禁链改动**：diff 命中 `scripts/check_*.py`、`scripts/gates.json`、
   `scripts/run_gates.py`、`.github/workflows/ci.yml`、`.githooks/` 时，逐条查
   ——断言有没有被删弱或放宽、基线是不是真红、有没有为了变绿而改断言、
   `check_gates_manifest.py --write` 是否同步跑过。
5. **正文结构**：分段齐全、`Closes` / `Refs` 用对（行为类必须 `Refs`）、
   分支 / 标题 / commit 三处都带 issue 号。
6. **行为类 PR**：核对验收是否真覆盖 issue 的复现路径，
   以及是否需要 `needs-live-verify` 而不是直接关单。
7. **出结论**：`APPROVE` 或 `REQUEST_CHANGES`，附证据（门禁原始输出、`文件:行号`）。
   **没有证据的结论无效。**

## 结论格式

写在 PR 评论里，三段缺一不可：

```
结论：APPROVE
复核动作：<跑了什么、读了哪些文件>
证据：
<门禁原始输出 / 文件行号 / 反例复现>
```

`REQUEST_CHANGES` 时额外给「最小修法」——指出**哪一处、改成什么**，
不要只说「再完善一下」。提交者按意见改完，**重新派一轮全新上下文的评审**，
不能拿上一轮的意见当本轮结论。

## 常见误判（都真实发生过或极易发生）

| 误判 | 为什么错 |
|---|---|
| 把 PR 正文当事实基础 | 正文是提交者写的，它正是被审查对象。只看正文等于让被测方出题 |
| 引用「CI 绿了」代替自己跑 | CI 跑的是合并前的快照，且可能是另一个 Python 版本；差异只能靠自己复现才发现 |
| 只看 diff 不看磁盘 | diff 里加了断言，但断言可能被 `if False` 包着；要打开文件读上下文 |
| 接受「只改门禁就变绿」 | 这说明门禁没钉住原症状，是本类 issue 的最严重形态 |
| 把 `SKIP` 当 `PASS` | `support` 档在无 PR 上下文时 SKIP 是正常的；但在 PR 上 SKIP 等于没验 |
| 取不到上下文就报绿 | 空文件列表会让「命中门禁链才要 `## 门禁改动`」静默失效，同一份正文从红变绿。取不全必须红 |
| 对文档 PR 放松 | 文档是本项目的记忆载体，断链等同于记忆缺失，`check_doc_links.py` 就是为此存在 |

## 与门禁的关系

- `scripts/check_pr_sections.py` 在 `support` 档（`scripts/gates.json`），
  校验正文分段与 `Closes`/`Refs`，CI 在 `pull_request` 事件上跑。
  **它只查结构，不查内容真假**——内容真假只有评审者能判。
- 下面这些东西里的标题与关键词**都不算数**，先剔除再匹配。判定必须按 CommonMark 来，
  用一条正则只能覆盖其中一类，剩下几类就是现成的绕过路径：
  - **围栏代码块**：开围栏最多缩进 3 空格；闭围栏同字符、不短于开围栏；到文末未闭合则余下全算代码。
  - **HTML 注释**：`<!--` 到 `-->` 之间；**到文末都没闭合时，余下整份正文在页面上都不可见**
    —— 这是让正文彻底隐身的最省事写法。一行里可能有多个 `<!--`，**闭合一个要接着找下一个**，
    只处理第一个的话 `<!-- x --> <!--` 就把未闭合的那半截藏起来了。
  - **4 空格 / 制表符缩进的代码块**：页面上是代码，`Closes #3` 写在里面不算关闭。
  - 注释在同一行闭合时，`-->` 之后的内容**不在行首**，不能算标题。
  - 反过来，**行内代码**（`` `...` ``）和**空行后的缩进代码块**里出现的 `<!--` 是字面量，
    不是注释起点。判错方向是假红：正文里引用这条规则本身就会触发它。
- 标题本身按 ATX 规则认：最多缩进 3 空格、`##` 后必须是半角空格或制表符。
  `##　影响面`（全角空格）不是标题，缩进 2 空格的 `##` 是标题 —— 两边都不能判错。
- 行尾统一归一化后再判定：`--body-file` 走 universal-newline 会把 CRLF 翻成 LF，
  而 `--pr` 与 CI 事件载荷会把 `\r\n` 原样带回来。不归一化就是「同一份正文两个结论」。
- 本地用 `--body-file` 自查时**必须显式带 `--files`**（确实没有改动文件就写 `--files` 不跟参数）。
  省略它等于宣称「没有改动文件」，门禁链判定会静默跳过、整份正文直接绿。
- 无 PR 上下文时（本地日常 `run_gates.py support`）它输出 `SKIP` 并退出 0，
  这是设计而非缺陷：把需要 PR 上下文的东西塞进 `ci` 档会把最便宜的一档弄脆。
- 但**有 PR 上下文却取不全**时必须红（退出 2）：事件载荷缺 `base.sha`/`head.sha`、
  或 `git diff base...head` 跑不通时，改动文件会是空列表，
  「命中门禁链才要 `## 门禁改动`」这一整段就静默失效，同一份正文会因环境抖动从红变绿。
- 评审结论**不进** `gates.json`：结论是人（会话）的判断，不是可重放的命令。
